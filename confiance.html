Avant tout

Ce que « bêta » veut dire ici — et ce que ça ne veut pas dire

Un numéro de version en 0.x signifie une chose précise : l'API JavaScript interne peut encore changer entre deux versions. Il ne signifie pas que le code est expérimental, peu testé ou instable en production.

Ce qui est stable

Le HTML que vous écrivez. Les balises <dsfr-data-*> et leurs attributs, documentés dans les spécifications des composants, sont le contrat public : un attribut n'est jamais retiré ni changé de sens sans dépréciation annoncée, remplaçant indiqué et période de transition.

Ce qui peut bouger

L'intérieur de la bibliothèque, entre deux versions mineures. C'est pourquoi la règle d'or est simple : chargez toujours une version exacte (dsfr-data@0.42.0), jamais @latest. Vous décidez quand changer.

Le 0.x a aussi un avantage : le projet livre vite. Un défaut signalé est en général corrigé dans la version suivante, et chaque version est documentée ligne par ligne dans le journal des modifications.

Question 1

Le risque de bug

Il y aura des bugs : c'est du logiciel. La question utile est : à quoi ressemble un bug pour vous, et comment est-il attrapé avant d'arriver sur votre site ?

À quoi ressemble un bug, concrètement

Ce qu'un bug peut faire, et ce qu'il ne peut pas faire
Ce qui peut arriverCe qui ne peut pas arriver
Un graphique ne s'affiche pas, ou affiche un message d'erreur explicite. Qu'un chiffre faux soit affiché sans avertissement : chaque valeur rendue est recalculée par un contrôle indépendant.
Une mise à jour de version demande d'ajuster un attribut (annoncé en console et dans le journal). Que votre page change sans que vous l'ayez décidé, si vous chargez une version exacte.
Une API de données change et le graphique se vide (voir nos limites). Que le reste de votre page soit affecté : les composants ne touchent ni votre CSS, ni votre JavaScript, ni votre CMS.

Comment les bugs sont attrapés

Le projet applique une règle inhabituelle pour une bibliothèque de dataviz : tout chiffre affiché a un contrôle. Au-delà des tests unitaires, un oracle indépendant — une seconde implémentation, écrite à part, qui n'importe rien de la bibliothèque — repart des données brutes et recalcule ce que la page affiche : indicateurs, graphiques, cartes, tableaux, exports. Un écart à la précision affichée est un échec bloquant. Une troisième voix, en Python standard, recalcule encore les mêmes attendus ; et en mode « vivant », c'est le serveur de données lui-même qui est interrogé pour recouper.

8 600tests unitaires exécutés à chaque changement
250contrôles numériques par l'oracle indépendant
35scénarios de bout en bout dans un vrai navigateur
WCAG 2 AAvérifié automatiquement (axe) à chaque changement

Tout cela est bloquant : une pull request qui fait tomber un contrôle ne peut pas être fusionnée. Et chaque contrôle a été vu en échec sur un défaut injecté volontairement — un test qui ne peut pas échouer ne prouve rien.

Quand vous trouvez un bug

Vous ouvrez une issue publique, avec la page ou le code qui le reproduit. Vous voyez la discussion, la correction, et la version qui l'embarque. Rien ne se passe en privé.

Vérifiez par vous-même

  • La doctrine de l'oracle et la liste des contrôles : tools/oracle/README.md
  • L'état de la CI, en temps réel : github.com/bmatge/dsfr-data/actions
  • Les issues ouvertes et fermées, pour juger du délai de correction : issues
  • La méthode d'évaluation d'une reproduction (quatre verdicts, chronométrage, vérification au navigateur) : EVALUER-UNE-REPRODUCTION.md
  • Le banc d'essai public, 110 dataviz branchées sur les portails de l'État : open-data-viz

Question 2

Pérennité et maintenance

La question derrière la question : que se passe-t-il pour mes pages si le projet s'arrête ? La réponse honnête tient en deux parties, parce que vous dépendez de deux choses différentes.

Ce dont vous dépendez, et ce qui arrive si cela disparaît
Vous dépendez de…Si ça disparaît
Ce qui s'exécute
chez vos visiteurs		 La bibliothèque dsfr-data et DSFR Chart, la bibliothèque officielle de l'État qui dessine les graphiques. Rien ne casse. Une version publiée est immuable et auto-hébergeable ; votre page continue sans limite de durée.
Ce qui aide vos équipes
à produire les pages		 Le Builder, cette instance en ligne, le Studio IA, le guide utilisateur. Vous perdez du confort, pas des pages. Le HTML publié ne dépend pas de l'outil qui l'a généré.

Le pire scénario est donc une perte de productivité pour vos équipes — jamais un incident sur un site en production.

Ce que vous possédez : votre HTML

Une visualisation dsfr-data est quelques lignes de HTML dont les attributs disent tout : quelle source, quel filtre, quelle agrégation, quel graphique. Il n'y a pas de JavaScript applicatif, pas de format propriétaire, pas de base de données à migrer. Ce HTML se lit sans la bibliothèque, par un humain comme par une IA, et se convertit vers un autre outil attribut par attribut. Il n'y a rien à exporter : vous l'avez déjà. 

<dsfr-data-source id="src" api-type="opendatasoft"
  base-url="https://data.economie.gouv.fr" dataset-id="industrie-du-futur"></dsfr-data-source>
<dsfr-data-query id="q" source="src"
  group-by="nom_region" aggregate="nombre_beneficiaires:sum:total" order-by="total:desc"></dsfr-data-query>
<dsfr-data-chart source="q" type="bar" label-field="nom_region" value-field="total"></dsfr-data-chart>

Pourquoi ça tient sans nous

  • Code ouvert, licence MIT — la même que le DSFR. Forkable, hébergeable, modifiable sans autorisation.
  • Versions immuables — le registre npm interdit de republier ou de retirer une version publiée. Ce que vous avez installé le restera.
  • Tout est dans le paquet — modules de carte, lecteur de données, fonds géographiques. À l'exécution, la bibliothèque ne charge rien depuis un CDN tiers ni depuis nos serveurs (détail des bundles dans l'architecture).
  • Le rendu est celui de l'État — dsfr-data prépare les données ; DSFR Chart, maintenu par le Service d'information du Gouvernement, dessine. Si dsfr-data s'arrête, ce qui dessine vos graphiques continue d'exister.
  • Standards du navigateur — les composants sont des Web Components natifs. Aucune obsolescence de plateforme à prévoir.

Ce que nous nous engageons à faire si le projet devait s'arrêter

Peu de choses, choisies parce qu'elles ne coûtent rien à tenir — c'est ce qui les rend crédibles.

  1. Chercher d'abord un repreneur public. La trajectoire visée est le versement aux communs numériques, pas l'arrêt.
  2. Prévenir au moins trois mois avant toute fermeture de cette instance et de son proxy, sur le dépôt et auprès des adoptants connus.
  3. Publier une dernière version corrigeant les défauts connus, avec le plan de sortie en tête du README.
  4. Archiver le dépôt en lecture seule — jamais le supprimer.

Vérifiez par vous-même

Le paquet publié ne contient l'adresse d'aucun de nos services :

grep -rl "miweb.run" package/dist     # aucun résultat attendu

Question 3

Sécurité

Deux questions distinctes : que fait le code dans le navigateur de vos visiteurs ? et comment le projet se protège-t-il contre les vulnérabilités ?

Dans le navigateur de vos visiteurs

  • Lecture seule. La bibliothèque lit des API de données publiques et affiche. Elle n'écrit nulle part.
  • Aucune donnée ne transite par nos serveurs. Le navigateur interroge directement la source (data.gouv.fr, Opendatasoft, INSEE…). Nous ne voyons ni vos données, ni vos visiteurs.
  • Ni cookie, ni traceur. La balise de mesure d'usage est désactivée tant que vous ne la configurez pas explicitement. Rien à déclarer au titre du RGPD.
  • Aucune clé d'API dans la bibliothèque. Elle n'en porte pas et n'en portera pas : une clé dans le navigateur est une clé publique. Les fonds de carte par défaut sont ceux de l'IGN, souverains et sans clé.
  • Compatible avec une politique de sécurité de contenu (CSP) stricte et livrée avec des empreintes d'intégrité (SRI) sur chaque script chargé depuis un CDN — en-têtes et CSP de référence dans la checklist sécurité du déploiement.

Dans la chaîne de production du code

Chaque modification passe dix contrôles de sécurité avant d'être fusionnée, et des analyses hebdomadaires rattrapent les vulnérabilités découvertes après coup :

Aucune exclusion silencieuse : toute règle ou vulnérabilité ignorée est documentée avec sa justification, son suivi et sa date de revue.

Si vous trouvez une vulnérabilité

Un canal privé est ouvert (GitHub Security Advisories). Engagement : accusé de réception sous 72 heures, correctif ou plan de mitigation sous 7 jours pour les vulnérabilités significatives. Détail dans la politique de sécurité.

À transmettre à votre RSSI. dsfr-data est une bibliothèque JavaScript front, open source (MIT), sans backend requis, qui lit des API de données publiques en HTTPS depuis le navigateur et n'envoie rien à des tiers. Chargée en version exacte avec SRI, compatible CSP default-src 'self' plus les domaines de vos sources. Chaîne de production auditée en continu (SCA, SAST, secrets, DAST), politique de divulgation publiée, dépendances suivies par Dependabot. Un proxy CORS est nécessaire uniquement pour les sources Grist ; il est à héberger par vos soins.

Vérifiez par vous-même

  • Les alertes et scans en temps réel : onglet Security du dépôt
  • Les licences des dépendances tierces : THIRD-PARTY-LICENSES.md
  • Sur une de vos pages : outils de développement, onglet Réseau — les seules requêtes sortantes visent vos fichiers et vos sources de données.

Question 4

Réversibilité : le test de débranchement

Plutôt qu'une promesse, un test. Cinq minutes, à faire dès votre première page, puis à chaque nouvelle. S'il passe, la fin du projet ne changerait rien pour vos visiteurs.

Trois étapes

  1. Ouvrez la page, puis les outils de développement (F12), onglet Réseau, et rechargez.
  2. Regardez d'où viennent les fichiers chargés. Ils doivent venir uniquement de votre domaine et de vos sources de données.
  3. Deux signaux d'alerte : une requête vers miweb.run (votre page dépend de notre instance) ; une adresse de script contenant @0, @latest ou aucun numéro de version (votre page changera un jour sans que vous l'ayez décidé).
Les trois résultats possibles du test de débranchement
Résultat du testNiveauCe qui peut casser
Aucune requête hors de chez vousAutonomeRien côté bibliothèque
CDN public, version exacte, empreinte d'intégritéFigéLa disponibilité du CDN — sans effet sur le contenu
Version flottante, ou proxy vers notre instanceDépendantUne mise à jour non choisie ; la fermeture de l'instance

Le cas Grist

Grist n'accepte pas les appels directs d'un navigateur : un widget Grist passe par un proxy. Sur un site public, ce proxy doit être le vôtre — quelques lignes de configuration que votre DSI trouvera dans le guide de déploiement. Si elle ne peut pas en héberger un, sachez que vos widgets Grist dépendent de notre instance. Les sources Opendatasoft, data.gouv.fr et INSEE n'ont pas cette contrainte.

Et si vous voulez partir un jour

Trois trajectoires, dont deux ne demandent aucun développeur :

  • Figer et garder. Une page figée fonctionne tant que l'API de sa source ne change pas — cela peut durer des années.
  • Passer à DSFR Chart nu. C'est déjà lui qui dessine vos graphiques ; seule la préparation des données est à refaire, et votre HTML la décrit attribut par attribut. Une IA sait faire cette conversion.
  • Reprendre le code, seul ou à plusieurs adoptants : le projet se construit en deux commandes, tests et oracle fournis (guide de contribution, architecture).

Liste de contrôle avant mise en production

  • La bibliothèque, le DSFR et DSFR Chart sont chargés à version exacte, ou auto-hébergés.
  • Le test de débranchement est passé : aucune requête vers miweb.run.
  • Si Grist : le proxy est le vôtre, ou la dépendance est acceptée et documentée.
  • Le HTML des widgets est versionné dans votre dépôt ou CMS, pas seulement dans nos favoris.
  • Quelqu'un est désigné pour remarquer un widget vide.

En toute franchise

Ce que nous ne promettons pas

Pour que vous ne nous l'attribuiez pas le jour où ça arrive.

  • Les changements des fournisseurs de données. Si une API source change, une page peut cesser d'afficher ses données. Figer dsfr-data ne protège pas de cela : un site vivant a besoin de quelqu'un qui regarde ses pages.
  • La compatibilité automatique entre versions. Tant que le projet est en 0.x, une mise à jour peut demander un ajustement. Vous choisissez quand.
  • La disponibilité des services tiers — CDN publics, fonds de carte communautaires.
  • Un niveau de service sur cette instance. chartsbuilder.miweb.run est un outil d'édition et de démonstration, pas une infrastructure de production pour vos pages.
  • Un support 24/7. Le support passe par les issues publiques, en heures ouvrées, par une équipe réduite.
